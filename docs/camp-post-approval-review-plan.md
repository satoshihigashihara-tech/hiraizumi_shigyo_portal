## 現状コードから分かった接続点

1. `save_camp_room_plan(uuid,bigint,bigint,jsonb)` は全員配置を原子的に保存するが、提出済み・審査中・修正待ち・許可済みの実配置差分を `room-change-review-required` で拒否する。この旧引数には理由・確認・申請期待版がないため、無条件にA10へ転送しない。
2. `private.lock_camp_application_for_staff` は新方式を拒否する。従来の `review_camp_application` はstayが存在するだけで拒否し、許可時にstayをINSERTする。これをそのまま新方式再審査へ使えない。
3. A7の未提出版は入力・当日JST日付・camp配置版・render contextを比較する。配置保存で古い確認版は失効するが、提出済み版の取得では現在入力や当日との一致を要求しない。
4. A7の現行配置contextは本人割当の配置版とcamp全体版の一致を要求する。一方、A4の終了処理は他者の割当版を更新しない。A9/A11後のmainでもこの差が残るかを確認する。現在配置の検査と、不変の提出済み文書を審査する検査を混同しない。
5. A3の全員保存は現在参加者をスナップショットへ入れるが、A4は解放済み行も含める。A10の新配置版では解放済み履歴を落とさず、既終了者を配置対象に復活させない。
6. 職員の現行配置取得は対象者ID・氏名・部屋・割当版だけを返し、申請期待版・提出版・stayを持たない。A10専用の取得契約を追加し、A5/A11の既存レスポンスを壊さない。

## 操作と状態遷移

対象は `usage_type='camp'` かつ `room_assignment_mode='eligible_roster'`。申請状態の列挙値を増やさず、許可を受けた事実は `application_status_events` と提出文書版から判定する。

| 操作前 | 実部屋差分がある場合 | stay・提出履歴 |
| --- | --- | --- |
| 申請なし | 配置変更だけ。申請を作らない | 作らない |
| draft | 配置変更だけ。入力を保持 | 作らない |
| submitted / under_review | `revision_requested`、理由・DB算定期限・履歴を記録 | 提出済みPDFを保持 |
| revision_requested | 状態を保持し、追加の部屋変更監査を記録 | 入力と過去PDFを保持 |
| approved | `revision_requested`、理由・DB算定期限・履歴を記録 | 正常な `before_move_in` stayをそのまま保持 |
| staying / moved_outを持つ申請 | 拒否 | 実入退去を保持 |
| released / disabled対象者 | 現在配置集合へ含めることを拒否 | A4の終了記録を保持 |

提出状態のない対象者でも、部屋変更の理由と確認は変更単位で必須とする。差分はDBが保存前後から求め、クライアント申告の「影響者一覧」を正としない。変更されない参加者へ修正依頼を追加しない。差分ゼロは新たな修正依頼・履歴・配置版を作らず、操作なしとして返す設計を基本にする。

修正期限はロック取得後のDB時刻を基準に、`min(JST確認日+4日の00:00, camp開始日の00:00)` とする。期限が現在以下、camp開始済み、実滞在開始済みなら全体拒否。既に修正待ちの場合は有効な既存期限を維持し、期限切れを部屋保存だけで自動再開しない。この追加操作の期限の扱いはA9確定契約との一致を実装前に再確認する。

本人の再提出はA9の経路で `revision_requested → submitted`。A10は職員用の `submitted → under_review`、`under_review → revision_requested / approved` を追加する。初回許可はstayなしを検査して1度だけ作成し、過去許可がある再許可は既存の正常な `before_move_in` stayを再利用する。過去許可あり・stayなし、許可履歴なし・既存stayあり、入退去日時付き入居前stayなどは不整合として拒否する。

不許可と取りやめはA4の期待版・参加終了・解放処理を使用する。A10のActionから「状態だけ変更→別RPCで解放」と分割しない。修正待ち・再提出後・再審査中はA4の入居処理で拒否されることを回帰試験する。

## DB・取得・Actionの設計案

以下はA9/A11マージ後に確定する追加API案。旧公開RPCの引数を変更しない。

- `get_staff_camp_room_change_context(target_camp_id)`：現在配置、操作前の申請ID／状態／updated_at、対象者updated_at、stay状態、現在の提出版ID、camp版を一つの読取スナップショットとして返す。未申請は明示的なnull。秘密情報・Auth結合・住所・他用途の情報は返さない。
- `change_camp_rooms_and_request_revisions(...)`：camp ID、取得時の名簿版・配置版、全有効参加者の配置、対象者ごとの期待状態（対象者更新時刻・申請ID／更新時刻、申請なしも含む）、理由、明示確認を受ける。成功は新配置版、実差分対象者、修正依頼対象申請、期限。全部同じトランザクションで確定する。
- `get_staff_camp_roster_application_review(target_camp_id,target_application_id)`：現在状態、審査対象の最新submitted文書版ID、正式snapshot、現在部屋、過去許可の有無、stayと操作可否、期待版を返す。保存済みの変更途中入力を「提出内容」と表示しない。
- `review_camp_roster_application(...)`：camp・申請ID、更新時刻、取得時配置版・本人割当版、審査対象の提出文書版ID、操作・理由を受ける。期待版なしの旧審査入口へ転送しない。A9が同等機能を実装していれば重複RPCを追加せず、確定契約を拡張する。

bigintは10進文字列、timestamptzは取得した小数6桁を保持する。RPCから返す版とIDも検査する。`42501`、`P0001/stale-update`、`40001`、`40P01`と固定業務エラーを画面用コードへ変換し、DB DETAILや生例外を返さない。

新しいAction・取得・validationはA10専用ファイルへ置く。必要な画面接続は既存職員配置ページ・審査詳細内へ追加し、A9の本人入力／確認UIやA11のPDF処理を書き直さない。画面には変更前後、修正依頼される本人、理由、期限を確認できる形で示す。エラー時は入力保持・再読込案内、送信中は重複操作防止。成功後は職員camp・配置・審査・名簿・本人申請・本人部屋・カレンダー・A11配置表の関連パスを再検証する。

## 原子性・不変条件

ロック順は施設（SQL026の団体期限処理を保持）→操作者と参照するprofile／職員権限→camp→部屋・mapping・設定→対象者ID順→申請ID順→stay申請ID順→割当対象者ID順→文書版・必要な採番／料金行。各トリガーが取る追加ロックも照合する。

すべての待機後に権限・有効profile・campモードと削除・対象者結合と参加・各期待版・日時・stay・配置・印字可能な部屋・定員・claimを検査する。REPEATABLE READは古いsnapshotで成功させず、既存施設guard更新による直列化失敗を許容する。監査失敗を含むエラーは全体ROLLBACKとする。

- 新しい全員配置と保存済み解放履歴を日別に検査し、部屋定員・施設定員を守る。部屋交換は更新途中の人数ではなく完成配置で判定する。
- 配置版は成功した変更で1増加。本人割当版は実部屋／期間／解放状態が変わる本人だけ増加。名簿版・氏名版は部屋変更だけで増やさない。
- 対象者追加後の未保存集合を許す場合も、保存時は最新の有効参加者全員を要求する。部分保存や対象者自動作成・再参加はしない。
- 現在配置行のID、claim IDと期間・未解放状態、初回確定時刻を保持。不変配置版と監査を追加し、過去配置版・解放履歴を更新しない。
- 受付番号・受付番号カウンター、chargesと月別明細のID／値、納付状態／日時／期限、既存stayのID／値、過去許可イベント、同意書、提出済みPDF全列・object・hashを保持する。新たな審査履歴と新提出版だけ追加する。
- A10で料金計算・返金・Storage削除・既存PDFの再生成を呼ばない。

## PDFと審査の区別

未提出確認版はA7/A9の現行性検査を使う。部屋変更前のPDF、変更前の要求キーの再利用、遅延callback、旧確認版からの提出を拒否する。入力は失わず、新版を生成して本人が同じversion IDを閲覧・確認・提出する。

職員審査は当該申請の**最新submitted版**を正本とする。過去の提出日や原本設定を後日の当日・active設定に置き換えない。対象camp／対象者／所有者、入力と提出の結び付き、本人割当ID・割当版・部屋・期間・提出hashを検査する。他人だけの配置変更によりcamp全体版が増えても、本人の実配置が不変のsubmitted版を「古い入力」と誤認しない。部屋が一度変わって元に戻っても、本人割当版が変わるため旧版を復活させない。

A8の `previously_approved` は「現在approvedか」でなく許可イベントの存在から算出する。初回審査前の修正は取り消し線あり、初回許可後の修正は取り消し線なし。再許可後も初回・再提出PDFの内容とhashを変更しない。

A11の文書版・ジョブを直接更新しない。配置変更による配置版増加とA9の正式氏名同期による氏名版増加が、A11の生成中／取得時の現行性検査へ確実に届くことを確認する。A11が過去版取得を提供する場合は、その既存契約を保持する。

## 実装後に実行するテスト計画

### DB単体・移行

新しい単体SQL、別接続競合SQL、共有fixtureをA10専用名で追加し、既存全件ランナーに登録する。過去SQLは変更しない。最後の依存SQL→A10移行の前後で、申請・対象者・配置・配置版・PDF版／ジョブ・stay・料金・納付・claim・監査の既存行が不変であることを比較する。

必須単体ケース：

1. 未申請、draft、submitted、under_review、revision_requested、approvedを混ぜた全員保存で、実差分本人だけが正しい遷移をする。変更なし・部屋交換・同じ部屋へ戻す場合も確認。
2. 初回提出→初回許可→部屋変更→新PDF再提出→再審査→再許可を2回以上実行し、受付番号・stay ID・charges／明細ID・納付値・初回許可・全過去PDF hashの保持を比較。
3. 理由空／超過、確認欠如、不正JSON、重複／別camp対象者・別用途申請、対象者不足／過剰、古い各期待版、期待「申請なし」の後の作成を拒否。

5. 再審査中の入居を拒否。修正中／再提出後の不許可と取消はA4で終了し、過去許可・料金・PDFを保持。
6. 本人変更前PDF・別版確認・同一キー別版・旧設定／JST日付・遅延生成結果からの提出を拒否。無関係な参加者のsubmitted文書の審査は継続できる。

### 別接続競合・権限

2 worker＋observerで実Lock待機を観測する。単にPromiseを並べた疑似競合で代替しない。

| 競合 | 必須結果 |
| --- | --- |
| A10変更 vs A10変更／A3保存 | 古い期待版の要求が失敗し、修正依頼・配置版を重複しない |
| A10変更 vs A9下書き作成・入力保存・PDF準備／完了・提出 | どちらが先でも変更と提出を取り違えない。古い状態から成功しない |
| A10変更／審査 vs 職員権限取消・profile停止 | ロック後に取消を反映し、未認可の成功を許さない |
| A10変更／審査 vs A4不許可・取りやめ・入退去 | 状態、解放、stay、PDFの一貫性を保つ。取りやめ者を再配置しない |
| A10変更 vs A2対象者追加・編集・無効化 | 全員集合・対象者期待版の不一致を拒否 |
| A10変更 vs A11生成開始／結果登録／認証取得 | 旧配置表を現行版として成功させない |
| A10再許可 vs 二重許可・納付更新 | stayを増やさず、並行の納付変更を上書きしない |
| A10変更 vs 部屋定員／mapping変更・camp／利用停止／個人／団体枠 | 最終定員・専有claim・共通施設排他を守る |
| 待機中のJST期限境界、REPEATABLE READ、監査失敗 | 期限／直列化／業務エラーで全体取消 |

匿名、一般利用者、他人、団体代表、停止職員、service_role、active職員のRPC権限と新規表のRLS／grantを検査する。旧camp更新入口は新方式IDを引き続き拒否。GET／HEAD／単一Rangeの本人・他人・職員取消・資格取消・存在推測・no-store・提出履歴保持もA7/A9回帰に含める。
