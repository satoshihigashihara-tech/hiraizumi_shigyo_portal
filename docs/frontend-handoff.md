# MVPの役割分担・共同作業の進め方

この文書は、東原（satoshihigashihara-tech）とフロント担当（nekonimatatabi）が2026年9月10日に合意した役割分担です。

## 最初に完成させる流れ

キャンプ利用者がログイン → 個人申請を入力・確認・提出 → 職員が確認・部屋割り・許可 → 利用者が結果を確認。

料金計算、受付番号、修正依頼・再提出、不許可、本人以外の申請を見られない制御も、この流れと一緒に実装します。団体申請など全体要件の残りは次の段階とし、この文書で全体の要件定義を置き換えるものではありません。

## 担当

| 作業 | 東原 | フロント担当 |
|---|---|---|
| 利用者向けトップ・ログイン画面 | 認証処理を接続 | 画面・入力欄・案内を作成 |
| 利用者ホーム・申請一覧・詳細 | 本人のデータを取得 | 表示・導線を作成 |
| 申請入力・確認・完了 | 保存・提出・入力検証・採番 | フォーム・確認表示・エラー表示を作成 |
| 修正依頼・結果確認 | 状態変更と理由を保存 | 状態と理由、次の操作を表示 |
| 職員画面 | 一覧・詳細・審査・部屋割りを作成 | 共通UIの使い方を共有 |
| Supabase・認証・権限・料金 | 作成・検証 | 表示に必要なデータを相談 |
| スマートフォン対応 | 職員画面を確認 | 利用者画面を作成・確認 |
| 公開・結合確認 | 公開設定と接続を担当 | 一緒に操作確認 |

フロント担当は、最初は架空のデータで利用者画面を作成します。画面を受け取った後、東原が実データの取得・保存処理を接続します。画面側でも入力漏れを案内し、最終的な入力・権限・定員の検査は東原がサーバー側で実装します。

## 最初に作る利用者画面

URLは `docs/routes.md` に合わせます。まずログイン画面と利用者ホームを小さな最初の提出単位にし、その後に申請画面へ進みます。

| 画面 | 表示する内容・操作 |
|---|---|
| トップ | サービス説明、キャンプ申請への入口、ログインへの入口 |
| ログイン | メール、パスワード、ログインボタン、エラー表示 |
| 利用者ホーム・一覧 | 自分の申請、利用期間、申請状態、詳細へのリンク、申請開始 |
| キャンプ選択 | 申請対象のキャンプ名、固定期間、申請期限 |
| 申請入力 | 氏名・住所・電話番号・緊急連絡先などの申請項目、下書き保存、確認へ進む |
| 申請確認 | 入力内容と期間、料金見込み、入力へ戻る、提出の確認と提出ボタン |
| 申請完了 | 受付番号、提出日時、申請済みの表示、詳細へのリンク |
| 申請詳細 | 内容、状態、修正理由、料金、許可後の部屋。下書き・修正依頼時は編集へのリンク |

申請項目の詳細は `docs/requirements.md` 第8章を参照します。今回の段階で対象外の機能は、動くように見せるボタンを置かず、必要なら準備中と表示します。「提出完了」は「利用確定」と表現しません。

## ファイルの担当境界

以下は実装時に用意する配置案です。現時点で全フォルダが存在するわけではありません。

| 担当 | 主な編集先 |
|---|---|
| フロント担当 | `app/page.js`、`app/page.module.css`、`app/login/`、`app/user/`、`app/components/`、画面ごとのCSS |
| 東原 | `app/staff/`、`app/actions/`、`lib/`、`supabase/`、公開・認証設定 |
| 事前に相談 | `app/layout.js`、`app/globals.css`、`package.json`、`package-lock.json` |

東原が利用者画面のファイルへ接続処理を追加するときは、対象を相手に伝え、同じファイルを同時編集しないようにします。フロント担当は画面用データをひとまとまりの仮データとして管理し、各画面へばらばらに埋め込まないようにします。

Next.js・JavaScript・通常のCSSを使用します。画面全体を一律にClient Componentにせず、入力やクリック操作に必要な部分を分けます。実装前にAGENTS.mdと、導入済みNext.jsの該当ガイドを確認します。

## 画面と処理をつなぐ前に決めること

東原が、対象画面の実装開始前に以下を共有します。

- 画面へ渡すデータの項目名と架空のサンプル
- 保存・提出処理へ渡す入力項目
- 成功したときの遷移先、失敗したときのエラー表示形式
- 状態ごとに表示するボタンと編集可能な条件

状態の保存値はDB設計に合わせます。最初に扱う値は `draft`（下書き）、`submitted`（申請済み）、`under_review`（審査中）、`revision_requested`（修正依頼）、`approved`（許可）、`rejected`（不許可）です。

フロント担当へ管理用秘密鍵を渡す必要はありません。仮データには実在する個人情報を使いません。

## コードの受け渡し

1. 招待を承認した相手が、共有リポジトリを自分のPCへ取得します。
2. 最新のmainから作業用ブランチを作ります。例：フロント担当は `codex/user-login-home`、東原は `codex/backend-auth`。
3. 各自のブランチで作業し、小さな画面・機能単位でコミットしてGitHubへpushします。
4. mainへ取り込むためのプルリクエスト（PR）を作ります。作った内容、確認方法、未接続の部分、画面のスクリーンショットを記載します。
5. もう一人が確認し、修正が済んだらmainへ取り込みます。フロント担当のPRは東原が確認します。
6. 次の作業前にmainの最新内容を取得します。

PRは「この変更を共有コードへ取り込んでください」という提出方法です。画面の作成途中でも、早めにPRで相談できます。

## 最初の共同確認

まず「ログイン画面と利用者ホームが仮データで表示される」状態をフロント担当が提出し、東原が認証とデータ取得を接続します。

接続後の最初の目標は「利用者がログインし、自分の申請1件の状態を確認できる」です。その後、下書き保存・提出、職員の審査・部屋割り、結果確認の順に接続します。

フロント担当の初回提出は、スマートフォン幅で横にはみ出さず、仮データであることと未接続の操作がPRから分かる状態を完成条件とします。ログイン画面と利用者ホームを1つのPRとして提出し、具体的な提出日時は2人で決めます。
