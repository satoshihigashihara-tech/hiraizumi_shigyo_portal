# 障害時の緊急対応

目的は被害拡大を止め、証拠を残し、安全に復旧すること。焦ってDB行、Authユーザー、Storageを直接削除しない。

## 最初の5分

1. 発生時刻、操作画面、役割、表示メッセージを記録する。秘密値と個人情報は記録しない。
2. 影響する操作を止め、別ブラウザで同じ更新を繰り返さない。
3. 誤ったアカウント削除の疑いがある場合だけ、下記のCron停止SQLを実行する。
4. GitHubのmain、Vercelの配備、Supabase SQL履歴の各時点を記録する。
5. 復旧前に対象UUID、状態、履歴を読取専用SQLで確認する。

## アカウント自動削除を緊急停止する

次のSQLは運用設定を変更する。クエリ名を`EMERGENCY pause account cleanup`として**保存し**、停止が必要な場合だけ1回実行する。

```sql
update cron.job
set active = false
where jobname = 'process-account-cleanup-every-minute';
```

停止確認は読取専用なので**保存しない**。

```sql
select jobname, schedule, active
from cron.job
where jobname = 'process-account-cleanup-every-minute';
```

`active = false`なら新しい定期呼出しは停止している。すでに開始済みの1回が終わる可能性はあるため、`account_cleanup_jobs`の`processing`件数も確認する。秘密値や利用者情報を画面共有しない。

## 状況別の対応

| 症状 | 直ちに行うこと | 行わないこと |
|---|---|---|
| 誤削除の疑い | Cron停止、対象UUIDと監査履歴を確認 | 同じメールで即再登録して過去記録へ接続しない |
| 申請・審査の二重操作 | 操作停止、最新状態と更新日時を再取得 | 古い画面から再送し続けない |
| 定員・日程の不整合 | 新規許可を止め、カレンダー・部屋・申請を読取確認 | 枠や部屋の行を単独で直接更新しない |
| 同意書の閲覧異常 | 閲覧操作を止め、Storageポリシーと対象パスを確認 | 公開バケットへ変更しない |
| 秘密値の露出 | 対象Secretを直ちに更新し、露出箇所を非公開化 | 古い秘密値を再利用しない |
| 公開画面の障害 | 直前の正常Vercel配備へ戻すことを検討 | 未確認コードを直接mainへ追加しない |

## 復旧条件

- 原因が説明でき、対象外利用者へ影響しない検証が成功している
- ローカルテスト、lint、production buildが成功している
- DB変更なら架空データのROLLBACK検証が成功している
- 自動削除なら誤対象0件、失敗ジョブの扱い、案内画面を確認している
- 変更内容、確認者、時刻、既知の制限を記録している

## 自動削除の再開

再開は原因修正と受入確認後に別作業として行う。停止中のジョブ状態を確認せず`active=true`へ戻さない。再開操作は担当者の明示承認を得てから実施する。
