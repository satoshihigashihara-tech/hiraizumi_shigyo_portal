# AI・新規参加者向けプロジェクト概要

## 1. このシステムは何か

「ひらいずみ志業ポータル」は、シェアハウスの利用希望者が町へ**使用許可を申請**し、町職員が審査・部屋・料金・納付・入退去を管理する試作版です。ホテルの空室を即時予約するシステムではありません。申請を送っても、その場で利用確定にはなりません。

最初に扱うのはスパルタキャンプ利用です。職員がキャンプ期間と対象メールアドレスを登録し、対象者だけが固定期間の個人申請を提出します。その後、地域活動の個人利用と団体利用を追加します。

## 2. 利用者と役割

- 未ログイン利用者：公開案内と公開カレンダーを見る。
- キャンプ利用者：自分が対象になっているキャンプへ個人申請する。
- 地域活動の個人利用者：将来、条件内の日程で個人申請する。
- 団体代表者・参加者：将来、招待を通じて団体利用を申請する。
- 町職員：申請、対象者、部屋、料金、納付、入退去、履歴を管理する。

本人の申請と職員業務以外から、住所・電話・緊急連絡先・同意書を取得してはいけません。団体代表者にも、参加者個人のこれらの情報を見せません。

## 3. 技術と責任分担

- Next.js App Router／JavaScript
- Supabase Auth、Postgres、RLS、Storage
- Vercelへの公開を予定
- バックエンド担当：DB、RLS、RPC、Server Actions、業務ルール、統合
- フロント担当：公開・利用者画面、フォーム、表示、レスポンシブ対応
- 接続と受入確認：2人で実施

画面からの更新はServer Actionを通し、重要な権限・期限・定員・状態判定はDBのRPCでも再検査します。ブラウザから送られるID、状態、金額、権限を信用しません。

## 4. 現在地

2026年9月10日時点で、Supabase接続、認証Action、基礎テーブル、キャンプ申請、採番、料金、職員のキャンプ作成・対象者追加、保護者同意書の非公開保存、職員の審査・部屋割り・許可処理があります。SQL `001`〜`011` はSupabaseへ適用済みです（009・010・011はSQL Editorの「Success. No rows returned」をユーザーが確認）。非公開バケット `guardian-consents` も作成済みです。

利用者・職員の業務画面は未作成です。コードやSQLが存在しても、ブラウザで正常系・権限違反・期限切れ・同時送信を確認するまでは機能完成と扱いません。詳細は [tasks.md](tasks.md) を参照してください。

作業ブランチ `codex/camp-room-approval` には、修正再提出の期限判定を直すSQL `009` と、キャンプ個人申請の部屋割り・許可を追加するSQL `010`、下書き作成入口の期限判定を直すSQL `011`、対応する職員Actionがあります。SQL 010は部屋別・施設15人の日別検査、状態・職員権限・更新日時の検査、職員専用監査履歴、許可時の入居前登録を行います。SQL 011適用後の単一接続の検証は218項目成功しました。複数接続での同時更新も7ケースすべて成功しました（19:47のユーザー提供画像で確認）。既存3つを含む職員の審査・部屋割りActionには `updatedAt` が必須となるため、SQL 010と更新後のActionをそろえて接続してください。地域活動・団体の部屋割り、画面接続は残作業です。

初回の検証では、下書き作成入口がトランザクション開始時刻の `now()` で判定していたため、処理途中の期限超過を拒否するケースで失敗しました。ユーザー確認後にSQL 011を作成・適用し、判定を `clock_timestamp()` へ変更しました。入力・返却値・下書き再利用の仕組みは維持しています。

検証用の `supabase/tests/camp_room_allocations_and_approval.sql` はSQL 001〜011を必要とします。ユーザーが更新後のファイル全体をSQL Editorで再実行し、2026年9月10日15:42の提供画像で `passed_checks = 218` と単一接続である旨の表示を確認しました。架空データと一時ヘルパーを使い、末尾の `ROLLBACK` で検証用変更を取り消す構成です。`npm run lint`・`npm run build` と関数差分の静的確認も成功しています。複数接続での定員競合・同一申請の競合・ロック待ち中の期限超過は、別の同時更新テストで確認済みです。実ログイン・実ファイル添付・画面接続は別途確認が必要です。

`supabase/tests/camp_room_allocations_concurrency.sql` の修正版を再準備し、A・B両方の実行成功後に `verify()` を実行しました。2026年9月10日19:47のユーザー提供画像で、ケース1〜7すべての `passed = true`、異なる接続ID（A: `100880`、B: `100891`）を確認しました。拒否コードはケース1〜4・6が `P0001`、ケース5が `40001`、ケース7が `42501` です。部屋・施設の残り1枠、部屋変更と許可の競合、二重許可、REPEATABLE READ、待機中の修正期限超過、待機中の職員停止を検証済みです。今回分もキャンプ7件・利用者25人・申請23件の削除結果と、`cleanup_completed = true` による専用スキーマの削除をユーザーが確認しました。受付番号カウンターは維持しています。詳しくは `docs/tasks.md` 第4.5節を参照してください。

初回の同時更新検証は、Bの条件分岐が分離レベル設定前にスナップショットを取得してSQLSTATE `25001` で停止し、Aもタイムアウトしました。検証コードをCOMMIT直後の設定へ修正し、実際の分離レベルの記録・検査を追加しました。失敗分はキャンプ7件・利用者25人・申請23件を削除し、専用スキーマの不存在と設定切り替えの単独検証にも成功してから再準備しています。受付番号カウンターは巻き戻していません。初回失敗分・修正版の成功分とも後片付けを確認済みです。

## 5. 必ず守る業務ルール

- 施設全体は15人。部屋別定員も超えない。
- キャンプ利用期間は職員が設定した固定期間。
- キャンプの対象メールと一致する本人だけが申請できる。
- 受付番号、料金、枠確保は提出成功時に行い、下書き時には行わない。
- 料金は1日300円、1暦月9,000円上限。
- 未成年者と18歳の高校生は、申請ごとに保護者同意書が必要。
- 同意書は非公開Storageに置き、公開URLや氏名・メールをパスへ含めない。
- 「申請状態」「納付状態」「滞在状態」を混同しない。
- 閲覧しただけで審査中などへ状態変更しない。
- 日時判定と表示は日本時間を基準にする。
