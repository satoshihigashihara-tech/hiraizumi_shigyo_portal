# ひらいずみ志業ポータル 発表者用手順

対象は1人5分の成果発表です。中央の3分をデモに使います。自主制作の試作版であり、平泉町公式サービスではありません。

## 発表の時間配分

| 時刻 | 内容 | 使用資料 |
|---|---|---|
| 0:00〜0:08 | Word申請の問題提起 | スライド1 |
| 0:08〜0:28 | Word、メール、紙、Excelに分かれた管理 | スライド2 |
| 0:28〜0:48 | 製品名と解決する範囲 | スライド3 |
| 0:48〜1:00 | 現在のmainと本番公開状況 | スライド4 |
| 1:00〜4:00 | ライブデモ | スライド5、ブラウザー |
| 4:00〜4:35 | 権限、定員、履歴の設計 | スライド6 |
| 4:35〜5:00 | 完成済みと開発中の区別、結び | スライド7 |

## 当日の短い発話原稿

PowerPointの発表者ノートもこの短縮原稿へ揃える。読み上げ速度は個人差があるため、下の秒数は進行枠であり、実測合格の記録ではない。実際の発表者が声を出して5分以内を確認する。

### スライド1 【0:00〜0:08】

申請書はWord。スマホでの記入が、最初の壁でした。

### スライド2 【0:08〜0:28】

Wordで記入し、メールで提出。職員は紙で許可し、Excelで料金を管理します。一つの申請が四か所に分かれるため、転記や状況確認に手間がかかります。

### スライド3 【0:28〜0:48】

そこで作ったのが、ひらいずみ志業ポータルです。利用者と職員が同じ申請を見ながら、審査、部屋、料金、入退去を確認します。自主制作の試作版です。

### スライド4 【0:48〜1:00】

コードとDBは反映済みです。公開画面から流れをご覧ください。本番のPDF生成は停止中です。

### スライド6 【4:00〜4:35】

利用者が見られるのは本人の申請です。職員操作もサーバーとDBで権限を確認します。施設と部屋の定員を同時操作でも守り、審査、納付、入退去を分けて記録します。画面だけでなく、データの整合性にも取り組みました。

### スライド7 【4:35〜5:00】

PDFは常設の変換先がないため、本番生成を停止しています。同意書アップロードはMVP対象外です。平泉で始める、その一歩を、手続きで止めない。これが、ひらいずみ志業ポータルです。

## 登壇30分前

1. 本番URL `https://hiraizumi-shigyo-portal.vercel.app` を開く。
2. 利用者用と職員用のブラウザープロファイルを分ける。
3. 架空アカウントだけを使い、通知、ブックマークバー、開発者ツールを閉じる。
4. 利用者側は申請一覧と自分の部屋、職員側はキャンプの名簿・部屋案を開いておく。架空申請が0件、職員セッションがない、取得エラーが出る場合は、認証画面の説明を最初から `fallback_demo.pdf` 3〜6ページで行う。公開画面だけをライブで示し、静的資料を本番画面とは説明しない。
5. `hiraizumi_shigyo_portal_mvp.pdf` と `fallback_demo.pdf` をローカルで開いておく。
6. Wi-Fiを一度切った状態でも `fallback_demo.pdf` を開けることを確認する。
7. `.env.local`、Supabase Secrets、Vault、Auth管理画面を閉じる。

## 3分デモ

### 0:00〜0:30 公開カレンダー

- 公開トップから利用状況カレンダーを開く。
- 表示は「申請可能」「利用不可」「受付開始前」だけと説明する。
- 氏名、受付番号、人数、内部理由を公開しないことを伝える。

### 0:30〜1:10 利用者の申請状況

- ログイン済みの利用者画面へ切り替える。
- 申請一覧から、受付番号、申請状態、料金、納付、滞在状態を見せる。
- 「提出完了は利用確定ではありません。職員の審査を待ちます」と説明する。

### 1:10〜1:50 部屋割りの情報分離

- 利用者の「自分の部屋」を表示する。
- 利用者には本人の割当だけを見せ、名簿全体や他参加者の部屋を表示しないことを説明する。
- 職員側の部屋案へ切り替え、対象者単位の配置と版競合をDBで検査することを説明する。

### 1:50〜2:40 職員の申請確認

- 職員画面へ切り替える。キャンプ申請詳細は `/staff/camps/[campId]/applications/[applicationId]`。IDは準備済み申請一覧のリンクから開く。
- 目的、審査状態、部屋、料金、納付、入退去、履歴が同じ申請へまとまることを示す。
- 発表中は本番データを変更せず、準備済み状態を閲覧する。

### 2:40〜3:00 まとめ

「申請する人と審査する人が、一つの申請を共有しながら手続きを進められます」と話し、スライド6へ戻る。

## 30秒以内の代替切替

通信待ちが8秒を超えた時点で調査を止める。次の一文を話す。

> ここからは、同じ流れを事前に用意した資料でご覧ください。

1. ブラウザーを閉じず、PDF表示へ切り替える。
2. `fallback_demo.pdf` の該当ページから説明を再開する。
3. 原因の説明や再ログインは発表後に行う。

| 症状 | 切替先 | 続ける説明 |
|---|---|---|
| 会場の通信断 | 代替PDF 1ページ目 | 公開トップから順番に全6ページ |
| Vercelが応答しない | 代替PDF 1ページ目 | 画面構成と利用者・職員の流れ |
| Supabaseの認証障害 | 代替PDF 3ページ目 | 利用者と職員の準備済み状態 |
| Supabaseのデータ取得障害 | 代替PDF 2ページ目 | 公開情報の限定と権限制御 |
| PDF生成が利用不可 | 代替PDF 3ページ目 | 常設Linux実行先が未指定のため安全側に停止していると説明 |
| 申請状態が想定と違う | 代替PDFの該当ページ | DBを直接変更せず、静止画で説明 |

## 現在の実装と開発中の範囲

### 公開本番で確認済み

- Vercelの公開トップと公開カレンダー
- 公開画面には氏名、受付番号、人数、内部理由を表示しない

### mainへ統合済み

- キャンプ対象者名簿、参加状態、職員の事前部屋案、利用者本人の部屋表示
- A7の不変PDF版・認証付き配信基盤
- A8の固定原本・日本語フォント・1ページ変換器とCI検査
- A9の画面内PDF確認・明示提出
- A10の提出後修正依頼・再確認・再提出・再審査
- A11の職員限定配置表PDF
- A12の総合受入、Auth削除競合防止、配置表PDFの可読性改善
- 既存の申請、審査、料金、納付、入退去、地域活動・団体利用

A9〜A12を含むSQL037〜040は本番Supabaseへ適用・保存し、検証結果が `all_passed=true` であることを確認済み。A12 PR #116はapplication、PDF renderer、PostgreSQL 17.6/18.4、Vercelの必須CIをすべて通過してmainへ統合済み。ただし、常設Linux変換実行先が未指定で、PDF生成active設定と本番部屋mappingは0件のため、PDF生成は安全側に停止する。発表では「本番でPDF生成・配信まで確認済み」と説明しない。

### 既知の制限・MVP対象外

- 常設Linux変換実行先、実JWT／Storage、本番生成後のスマートフォン確認提出は未受入
- PDF生成active設定と本番部屋mappingは0件。総合受入だけを理由に有効化しない
- 保護者同意書アップロード。Issue #85ではMVP対象外・本番未対応として整理済み

## 想定質問

### 平泉町が運営する公式サービスですか

いいえ。自主制作の試作版です。既存業務と要件資料をもとに、運用方法を提案しています。

### 一般的な宿泊予約サービスですか

いいえ。利用者が申請し、町職員が活動内容を審査して使用を許可する流れを支えます。

### 個人情報は団体代表者にも見えますか

代表者へ返す情報を必要最小限に限定します。住所、電話、緊急連絡先、同意書は表示しません。

### 通信が切れた場合はどうしますか

発表では30秒以内にローカルPDFへ切り替えます。実運用では更新操作を止め、状態と履歴を確認してから復旧します。

### 申請PDFや配置表PDFは本番で作れますか

現在は作れません。DB、認可、画面、変換器のコードとSQL037〜040は反映済みですが、常設Linux変換実行先が未指定です。不完全な状態で生成を始めず、active設定0のまま安全側に停止します。発表ではローカル代替PDFを使います。

### 今後追加するものは何ですか

A12の総合受入とSQL040の本番適用・検証は完了しました。次は常設Linux変換実行先の指定と、実JWT／Storageを使う本番E2E受入です。保護者同意書アップロードはMVP対象外です。mainへ統合済みのコードと、本番で利用可能な機能を分けて説明します。
