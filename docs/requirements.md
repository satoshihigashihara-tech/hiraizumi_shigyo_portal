# ひらいずみ志業ポータル 要件定義書

> 平泉町志業シェアハウス利用申請・管理システム

| 項目 | 内容 |
|---|---|
| 文書版 | 1.0 |
| 作成日 | 2026年9月9日 |
| 対象 | スパルタキャンプ自主制作として開発する試作版 |
| 開発体制 | 2人 |
| サービス名 | ひらいずみ志業ポータル |
| 文書の位置付け | 試作版の設計・実装・受入確認に用いる基準。本運用前に町への確認事項を確定し、必要な変更を反映する |

## 1. 目的

ひらいずみ志業ポータルは、平泉町志業シェアハウスの利用案内、使用許可申請、審査、部屋割り、料金、納付、入退去を一元管理するWebアプリケーションである。

本システムが扱うのは「利用予約」ではなく「使用許可申請」である。利用者が申請を提出した時点では利用は確定せず、町職員の審査と許可を経て利用が確定する。

試作版では、現在のスパルタキャンプ利用に加え、キャンプ開催期間外に個人または団体が地域活動を目的として利用する仕組みを提案・検証する。地域活動利用の正式な制度化は、本運用前に町の確認を必要とする。

## 2. 背景と解決する課題

現行運用では、利用希望者がWord形式の使用許可申請書へ記入し、メールなどで町へ提出する。町職員は申請受付、内容確認、紙の使用許可通知、Excelによる料金管理、納付書の発行、部屋割り、対面での入退去確認を行っている。

本システムは、次の課題を解決する。

- スマートフォンではWord申請書を編集しにくい
- 記入漏れ、ファイルの添付漏れ、メールの見落としが生じ得る
- 申請、審査、部屋、料金、納付、滞在状況が複数の媒体に分散している
- 利用者が申請状況や利用可能日を確認しにくい
- 町職員に転記、照合、進捗確認の作業が発生する
- スパルタキャンプ以外の利用可能性が外部から分かりにくい

## 3. 基本方針

1. 正式な使用許可申請書（様式第1号）の項目を基本とする。
2. 一般のホテル予約のような即時確定は行わない。
3. 一般観光目的の宿泊は対象にしない。
4. 地域活動に該当するかはシステムで自動判定せず、町職員が申請内容を審査する。
5. 個人情報は利用目的に必要な範囲で収集し、役割ごとに閲覧範囲を制限する。
6. 試作版で確定した仕様と、本運用前に町が決定する事項を分けて管理する。
7. 施設全体の定員は、町への確認結果に基づき15人とする。

## 4. 対象範囲

### 4.1 利用区分

| 利用区分 | 概要 | 日程の決め方 |
|---|---|---|
| スパルタキャンプ利用 | キャンプ参加者のうちシェアハウス利用を希望した人が個別に申請する | 職員がキャンプごとの固定期間を設定し、利用者はその期間に従う |
| 地域活動利用・個人 | 町内での学習、調査、交流、起業準備、地域振興活動などを行う個人が申請する | 公開カレンダーから条件内の日程を選ぶ |
| 地域活動利用・団体 | 同じ目的と日程で活動する2人以上の団体が申請する | 代表者が日程を選び、団体全体で期間を確保する |

「地域活動利用」は試作版での仮称である。

### 4.2 対象者

- スパルタキャンプ参加者
- スパルタキャンプ修了生で、町内での起業準備または地域振興につながる活動を行う人
- 町が認める地域活動を行う個人または団体
- 大学ゼミ、研究室、自治体・企業の視察研修、地域イベントの参加・運営団体など

### 4.3 対象外

- スパルタキャンプ本体への参加申込み、選考、受講管理
- 一般観光客向けの宿泊予約
- 申請と同時に宿泊を確定する機能
- オンライン決済および銀行との自動連携
- 納付状況による自動キャンセルまたは自動入居停止
- 正式な使用許可通知書、納付書などのPDF生成・電子交付
- 地域活動に該当するかの自動判定
- 宿泊を伴わない「共用部分のみ」の利用申請
- 団体代表者による参加者の住所、電話番号、緊急連絡先、同意書の代理入力
- 団体内で誰がどの部屋を使うかの氏名単位の管理
- 独立した活動計画書の添付
- 退去時の設備問題や口頭説明内容を記録する機能
- 早期退去時の自動減額・返金
- 利用者自身によるアカウント削除
- 画面上から全デモデータを初期化する機能
- 独自のバックアップ・復旧機能

## 5. 利用者と権限

| 役割 | 主な操作 |
|---|---|
| 未ログイン利用者 | 地域活動利用の条件、料金、公開カレンダーの閲覧 |
| スパルタキャンプ利用者 | 対象キャンプの固定期間に対する個人申請、申請状況・料金・部屋・滞在情報の確認 |
| 地域活動の個人利用者 | 日程選択、個人申請、修正、キャンセル申請、継続申請 |
| 団体代表者 | 団体共通情報の登録、参加者招待、提出状況の確認、団体の修正・キャンセル手続き |
| 団体参加者 | 招待された団体への参加、自分の個別申請の提出・修正、結果確認 |
| 町職員 | 全申請の審査、日程、対象者、部屋、料金、納付、入退去、連絡先、履歴の管理 |

### 5.1 権限ルール

- 一般利用者は、自分のプロフィールと自分の個別申請だけを閲覧・更新できる。
- 団体代表者は、団体共通情報、参加者氏名、参加者ごとの提出・審査状態を閲覧できる。
- 団体代表者は、参加者の住所、電話番号、個人の緊急連絡先、保護者同意書を閲覧できない。
- 団体参加者は、他の参加者の個人情報を閲覧できない。
- 町職員は、業務に必要な全情報を閲覧・更新できる。
- 職員アカウントは複数登録できる。試作版では職員間の権限を細分化しない。
- 職員権限はSupabase側からのみ付与し、利用者が登録時に選択できないようにする。
- 上記の制限は画面表示だけでなく、SupabaseのRow Level Securityでも実施する。

## 6. 共通業務ルール

### 6.1 施設定員と部屋

町への確認結果に基づき、施設全体の定員を15人とする。

| 部屋名 | 定員 |
|---|---:|
| 桐 | 1人 |
| 藤 | 1人 |
| 梅 | 2人 |
| 竹 | 2人 |
| 松 | 2人 |
| あやめ | 2人 |
| もみぢ | 2人 |
| さくら | 3人 |
| 合計 | 15人 |

- 各部屋の定員と施設全体の15人を超える割当てを禁止する。
- 相部屋を認める。
- スパルタキャンプ利用者と地域活動の個人利用者は、職員が個人ごとに部屋を割り当てる。
- 団体利用では、職員が使用する部屋と各部屋の利用人数を割り当てる。参加者の氏名単位の配置は団体内で決める。
- スパルタキャンプ利用と地域活動の個人利用は、本人の部屋割りが完了するまで「許可」にできない。
- 団体全体は、全参加者の個別申請が許可され、団体の割当人数と参加人数が一致し、部屋別定員と施設定員を満たすまで「許可」にできない。
- 許可後も職員は部屋割りを変更できる。変更理由、変更前後の内容、操作者、日時を履歴に残す。

### 6.2 日付と時刻

- 申請期限、修正期限、提出日時、状態変更日時は日本時間で扱う。
- 画面では「2026年9月8日 23:59」のように表示する。
- データベースでは時刻を一貫した形式で保存し、表示時に日本時間へ変換する。
- 料金日数は時刻ではなく開始日と終了日で計算し、両方の日を含める。

### 6.3 受付番号

- 個人申請と団体全体の申請に、それぞれ受付番号を自動発行する。
- 形式は「SG-西暦-連番」とする。例は「SG-2026-0001」とする。
- 連番は運用年度ごとに1から開始する。
- 団体全体の受付番号と参加者の個別受付番号は別に発行する。

### 6.4 申請状態・納付状態・滞在状態

申請の審査、料金の納付、実際の入退去は別の状態として管理する。

| 分類 | 状態 |
|---|---|
| 個人申請・団体参加者申請 | 下書き、申請済み、審査中、修正依頼、許可、不許可、キャンセル申請中、キャンセル済み |
| 団体全体 | 下書き、申請中、審査中、修正依頼、許可、不許可、キャンセル申請中、キャンセル済み |
| 納付 | 未納、納付済み |
| 滞在 | 入居前、滞在中、退去済み |

- 申請が許可された後も、申請状態は「許可」として履歴に残す。
- 入退去は滞在状態で管理する。
- 「許可」かつ「退去済み」は、利用が終了した申請として扱う。
- 納付状態は、申請状態と滞在状態を自動では変更しない。
- 未納のまま納付期限を過ぎた場合は「期限超過」を表示するが、納付状態そのものは「未納」のままとする。

## 7. 認証とアカウント

### 7.1 共通

- Supabase Authのメールアドレス・パスワード認証を使用する。
- ログイン、新規登録、ログアウトを必須機能とする。
- 試作版ではメールアドレス確認を必須にしない。
- 地域活動利用者は、自分のメールアドレスで新規登録できる。
- 実在する個人情報を使わない、役割別の架空デモアカウントを用意する。
- デモアカウントは、職員、キャンプ利用者、地域活動の個人利用者、団体代表者、団体参加者の5種類とする。
- デモアカウント情報と初期データの作成手順はREADMEへ記載する。

### 7.2 スパルタキャンプ対象者

- 職員がキャンプごとに対象者のメールアドレスを事前登録する。
- 登録済みメールアドレスと一致する利用者だけが、そのキャンプの申請画面を開ける。
- 同じメールアドレスは、将来の別キャンプの対象者として再登録できる。
- 別キャンプへ登録する場合は、過去の対象者記録とは別の対象者情報として保存する。

### 7.3 利用終了後の初期化

利用者の退去が完了し、次のいずれにも該当しない場合は、認証アカウントと再利用用プロフィールを自動削除して初期化する。

- 入居前または滞在中の別申請がある
- 下書き、申請済み、審査中、修正依頼、キャンセル申請中の申請がある
- 将来の許可済み申請または継続滞在申請がある
- 未終了の団体へ参加している
- 未終了の団体を代表者として管理している

「許可」かつ「退去済み」の過去申請だけが残る場合は、初期化できる。判定は退去処理、申請の終了、団体の終了の各時点で再実行する。

宿泊しない団体代表者は、管理する団体の利用が終了し、他に未終了の申請・団体がない時点で初期化する。職員アカウントは自動初期化の対象外とする。

申請、許可、料金、納付、状態変更履歴は町の管理記録として残す。アカウント削除後の記録は職員だけが閲覧でき、新しく同じメールアドレスで登録した利用者からは閲覧できない。保存期間は町への確認事項とする。

利用者が利用前に不許可またはキャンセル済みとなり退去処理が存在しない場合は、本人から町への連絡に基づき職員がアカウントを停止できる。

## 8. 共通申請機能

### 8.1 申請項目

様式第1号を基本とし、次の情報を扱う。

| 区分 | 項目 |
|---|---|
| 申請者 | 住所、団体名、氏名または代表者名 |
| 使用者 | 住所、氏名、電話番号 |
| 緊急連絡先 | 住所、氏名、電話番号 |
| 使用内容 | 使用期間、使用箇所、使用目的または変更内容、特記事項 |
| Web補助項目 | メールアドレス、未成年等の該当確認、保護者同意書、キャンプ利用時の相部屋希望 |

- 年齢と性別は必須入力にしない。
- 地域活動利用では「活動目的」と「平泉町内で行う活動」を入力する。
- 活動計画書を別ファイルとして提出する機能は設けない。追加情報が必要な場合は職員が修正を依頼する。
- 使用箇所はプルダウンで「共用部分及び2階個室」を選択させる。
- 具体的な部屋名は申請者に選ばせず、職員が部屋割りで登録する。
- スパルタキャンプ利用と地域活動の個人利用では、申請者と使用者を同一人物として扱う。
- 団体利用では、団体代表者を申請者、各参加者を使用者として扱う。参加者の個別申請には団体共通情報を紐づける。
- 申請者本人が使用者である場合は、住所と氏名を自動入力できるようにする。
- 氏名、住所、電話番号、緊急連絡先はプロフィールへ保存し、次回申請や継続申請へ初期表示する。利用者は申請ごとに確認・修正できる。

### 8.2 保護者同意書

- 未成年者および18歳の高校生は、申請ごとに保護者同意書を提出する。
- アップロード形式はPDF、JPEG、PNGのいずれかとする。
- 1申請につき1ファイル、最大5MBとする。
- ファイルはSupabase Storageの非公開領域へ保存する。
- 閲覧できるのは提出した本人と町職員だけとする。
- 指定様式の有無は町への確認事項とする。

### 8.3 入力・下書き・提出

- 「下書き保存」ボタンを設け、後から入力を再開できるようにする。
- 自動保存は行わない。
- 下書きは日程や定員を確保しない。提出時に最新の空き状況を再確認する。
- 必須項目の未入力、電話番号・メールアドレスの形式不正、日程・人数条件の違反がある場合は送信しない。
- エラー理由を該当項目の近くへ表示し、入力済みの内容を保持する。
- エラー箇所へ移動できるようにする。
- 送信前に申請内容の確認画面を表示する。
- 「入力内容を確認し、申請を提出します」への確認後だけ提出できるようにする。
- 送信処理中はボタンを無効化し、サーバー側でも二重登録を防ぐ。
- 提出成功後は受付番号、提出日時、現在の状態を表示する。
- 提出後は編集を禁止し、「下書き」または「修正依頼」のときだけ利用者が編集できる。
- 修正後の再提出では、個人申請を「申請済み」へ戻す。

## 9. スパルタキャンプ利用

### 9.1 キャンプ設定

職員は、キャンプごとに次の情報を登録・編集する。

- キャンプ名
- シェアハウスの利用開始日と利用終了日
- 申請期限
- 対象者メールアドレス

キャンプ本体への申込みとシェアハウスへの申請は別の手続きとする。キャンプ申込み時にシェアハウス利用希望を確認済みであるため、システム上の募集人数は設定しない。

対象メールアドレスは複数行の入力欄へ貼り付けて一括登録できるようにし、形式不正と重複を表示する。

### 9.2 利用者の申請

- 利用者は日程を選択できない。
- 職員が設定した期間を申請へ自動反映する。
- キャンプ名、対象メール、期間など、登録済み情報を可能な範囲で自動入力する。
- 使用箇所は「共用部分及び2階個室」とする。
- 相部屋について「相部屋可」または「個室希望」を入力できる。希望は部屋割りの参考情報であり、個室を保証しない。
- キャンプ期間中に一時的に不在となる日があっても、設定された利用期間全体を部屋確保と料金計算の対象とする。

### 9.3 期限とキャンセル

- 申請期限を過ぎた対象者は、新規申請できない。
- 期限後は「受付期間が終了しました。町へ直接お問い合わせください」と表示する。
- 職員は必要に応じて期限を延長できる。
- 利用者用のキャンセル操作は設けない。
- 利用者は町へ直接連絡し、職員が申請を「キャンセル済み」へ変更する。
- 個別申請がキャンセルされても、職員が設定したキャンプ期間全体は地域活動利用へ開放しない。

## 10. 地域活動利用の共通ルール

### 10.1 申請可能期間

- 利用開始日と利用終了日の両方が、申請日から60日以内にある日程だけを選択できる。
- 61日目以降は「受付開始前」と表示して選択不可にする。
- 利用開始日の14日前までに申請を開始する。
- 個人申請では提出、団体申請では団体を「申請中」にして期間を確保する操作を、申請開始として扱う。
- 利用期間は1泊2日以上、14泊15日以内とする。
- 職員によるキャンプ期間・利用停止期間の設定には60日制限を適用しない。

### 10.2 利用対象

- 地域活動利用者は、活動目的と平泉町内で行う活動を入力する。
- 一般観光目的では申請できない。
- 日程条件を満たしても利用は確定せず、活動内容を町職員が審査する。

## 11. 地域活動の個人利用

1. 未ログイン利用者は、利用条件、料金、公開カレンダーを確認する。
2. 利用者は登録・ログインし、申請可能な開始日と終了日を選ぶ。
3. 申請情報を入力し、確認後に提出する。
4. 提出処理と同時に各利用日について1人分の定員を確保する。
5. 職員が審査、部屋割り、許可または不許可の処理を行う。
6. 許可後は料金、納付状況、部屋、緊急連絡先、滞在状況を確認できる。

個人同士は同じ期間に利用できる。有効な個人申請が同じ日に15人へ達した場合、その日は新しい個人申請で選択できない。

スパルタキャンプ期間、団体が確保した期間、職員が設定した利用停止期間とは重複できない。

地域活動の個人利用者が入居前にキャンセルする場合は、理由を入力して「キャンセル申請中」にする。職員が確認して「キャンセル済み」に変更するまで、1人分の定員を確保し続ける。滞在開始後はこの操作を表示せず、早期退去の手続きで扱う。

## 12. 地域活動の団体利用

### 12.1 基本条件

- 新規申請時の宿泊者数は2人以上15人以下とする。
- 代表者は宿泊しなくてもよい。
- 代表者が宿泊する場合は、自分も参加者として個別申請を提出する。
- 同じ期間に利用できる地域活動団体は1団体だけとする。
- 団体利用期間は施設全体を確保し、他団体および地域活動の個人利用と重複させない。

### 12.2 団体共通情報

代表者は、次の共通情報を登録する。

- 団体名
- 利用期間
- 使用箇所
- 使用目的（活動目的）
- 平泉町内で行う活動
- 特記事項
- 参加予定人数

代表者が共通情報を確定し、団体を「申請中」に変更した時点で日程を確保する。

### 12.3 参加者招待

- 団体ごとに推測されにくい共通招待リンクを1つ発行する。
- 共通コードの手入力も補助機能として用意する。
- 代表者がリンクまたはコードを自分で参加者へ共有する。
- システムから招待メールは送信しない。
- 参加人数が参加予定人数へ達した場合は、それ以上参加できない。
- 招待リンクの有効期限は参加者の提出期限と同じとする。
- 代表者はリンクを無効化・再発行できる。
- リンクを再発行しても、すでに参加した人と提出期限は維持する。
- 各参加者はログイン後、自分の個別使用許可申請を提出する。

### 12.4 参加者提出期限

- 標準期限は団体を「申請中」にした日から7日後の23:59（日本時間）とする。
- 例として、9月1日に申請中へ変更した場合の初期期限は9月8日23:59とする。
- システムが標準期限を初期設定し、職員が必要に応じて変更できる。
- 代表者と参加者には、職員が確定した締切日時を表示する。
- 期限は利用開始日の前日を越えない。
- 期限変更、参加者の追加・削除、招待リンクの再発行によって、提出済み申請を失わない。
- 期限までに全員が提出しなければ、団体全体と紐づく未終了の参加者申請を自動的に「キャンセル済み」にし、日程を解放する。

### 12.5 参加者変更と審査

- 初回の「申請中」で、提出期限内かつ団体が「審査中」へ移る前であれば、代表者は参加者を追加・削除できる。
- 参加者変更によって提出期限は延長しない。
- 変更後も2人以上15人以下を満たす。
- 参加予定者全員が個別申請を提出すると、団体全体を自動的に「審査中」へ変更する。
- 団体が「審査中」になった後は参加者構成を固定し、変更には職員の修正依頼を必要とする。
- 職員は、団体の利用目的と町内活動を先に確認し、その後に参加者の個別申請を審査する。
- 団体自体を「不許可」にする場合は、未終了の参加者個別申請も「不許可」にし、共通する理由を記録する。
- 参加者の個別申請は、職員が明示的に審査開始操作をした時点で「審査中」になる。
- 団体全体を「許可」にできるのは、全参加者の個別申請が許可され、部屋割りが完了し、人数と割当人数が一致した場合だけとする。

### 12.6 修正依頼

- 参加者の個別申請が不許可となった場合、団体全体を「修正依頼」にする。
- 代表者は対象者を削除するか、別の参加者へ交代できる。
- 交代者は期限内に自分の個別申請を提出する。
- 修正期限の標準は、修正依頼日から3日後の23:59（日本時間）とする。
- 例として、9月1日の修正依頼に対する初期期限は9月4日23:59とする。
- 職員は修正期限を変更できる。
- 期限内に条件を満たさなければ、団体全体と紐づく未終了の参加者申請を「キャンセル済み」にし、日程を解放する。

### 12.7 キャンセル

- 団体の滞在開始前に代表者が理由を入力すると、団体全体を「キャンセル申請中」にする。
- 職員が確認して「キャンセル済み」にするまで日程を確保する。
- キャンセル確定時は、紐づく未終了の参加者申請も「キャンセル済み」にする。
- 許可後に一部の参加者だけがキャンセルする場合は、代表者が画面に表示された町の連絡先へ電話する。
- 職員が対象者を「キャンセル済み」にし、参加人数と部屋割りを更新する。
- 新規団体は2人以上を必要とするが、許可後の人数減少で1人になった場合は職員判断で継続できる。
- 許可後の減員で団体利用を継続する場合、団体が確保した期間を個人利用へ開放しない。
- 全参加者が利用しなくなった場合は、団体全体も「キャンセル済み」にする。
- 参加者が滞在を開始した後は団体のキャンセル申請操作を表示せず、町への電話連絡と早期退去の手続きで扱う。

## 13. 状態遷移

### 13.1 個人申請・団体参加者申請

| 現在の状態 | 操作・条件 | 次の状態 |
|---|---|---|
| 下書き | 利用者が提出 | 申請済み |
| 申請済み | 職員が審査開始 | 審査中 |
| 審査中 | 職員が修正理由を入力 | 修正依頼 |
| 修正依頼 | 利用者が修正して再提出 | 申請済み |
| 審査中 | 職員が必要な確認を完了して許可 | 許可 |
| 審査中 | 職員が理由を入力して不許可 | 不許可 |
| 申請済み・審査中・修正依頼・許可 | 地域活動利用者が理由を入力 | キャンセル申請中 |
| キャンセル申請中 | 職員が確認 | キャンセル済み |
| 申請済み・審査中・修正依頼・許可 | キャンプ利用者からの連絡後、職員が処理 | キャンセル済み |

「キャンセル申請中」は地域活動利用だけで利用者が選択できる。スパルタキャンプ利用者にはキャンセル操作を表示しない。
許可後のキャンセル遷移は滞在状態が「入居前」の場合だけに適用し、「滞在中」では早期退去として扱う。
スパルタキャンプ利用と地域活動の個人利用は、部屋割り完了を許可条件とする。団体参加者の個別申請は単独で部屋を割り当てず、全参加者の個別許可後に団体全体の部屋割りを行う。

### 13.2 団体全体

| 現在の状態 | 操作・条件 | 次の状態 |
|---|---|---|
| 下書き | 代表者が申請開始 | 申請中 |
| 申請中 | 予定する全参加者が提出 | 審査中 |
| 申請中 | 提出期限切れ | キャンセル済み |
| 審査中 | 団体情報または参加者に修正が必要 | 修正依頼 |
| 修正依頼 | 期限内に再提出条件を満たす | 審査中 |
| 修正依頼 | 修正期限切れ | キャンセル済み |
| 審査中 | 全参加者許可・部屋割り完了 | 許可 |
| 審査中 | 団体の利用目的などを認めない | 不許可 |
| 申請中・審査中・修正依頼・許可 | 代表者が理由を入力 | キャンセル申請中 |
| キャンセル申請中 | 職員が確認 | キャンセル済み |

「申請中」では、「8/10人提出済み」のように提出数を併記する。
許可後のキャンセル遷移は団体の滞在開始前だけに適用する。

### 13.3 滞在

| 現在の状態 | 操作 | 次の状態 |
|---|---|---|
| 未設定 | 申請を許可 | 入居前 |
| 入居前 | 職員が対面で入居確認 | 滞在中 |
| 滞在中 | 職員が対面で退去確認 | 退去済み |

## 14. カレンダーと利用枠

### 14.1 公開カレンダー

- ログイン前でも地域活動利用のカレンダーを閲覧できる。
- 「申請可能」「利用不可」「受付開始前」を表示する。
- 利用不可日は、色、斜線、文字を組み合わせて識別できるようにする。
- 申請者名、団体名、申請状態、利用不可の内部理由は公開しない。
- 利用不可日は理由にかかわらず「利用不可」と表示する。

### 14.2 職員カレンダー

- スパルタキャンプ、団体利用、個人利用、利用停止期間を区別して表示する。
- 日付を選択すると、受付番号、利用者または団体名、人数、状態を確認できる。
- 職員はスパルタキャンプ期間と利用停止期間を登録・編集・削除できる。
- 利用停止期間には、清掃、修繕、町行事などの内部向け理由を登録できる。
- 既存の有効な申請と重なる期間登録・変更は保存しない。
- 競合する受付番号、利用者または団体、期間、状態を表示し、該当申請の変更やキャンセル後に保存できるようにする。
- 固定のデモ日程は要件としない。職員が実際の日程または架空の日程を入力する。

### 14.3 利用枠を確保する状態

| 対象 | 確保する状態 | 解放する状態・契機 |
|---|---|---|
| スパルタキャンプ | 職員が登録している全期間 | 競合申請への対応後、職員が期間を削除 |
| 利用停止期間 | 職員が登録している全期間 | 職員が期間を削除 |
| 地域活動・個人 | 申請済み、審査中、修正依頼、許可、キャンセル申請中 | 不許可、キャンセル済み、確認済み早期退去日の翌日以降 |
| 地域活動・団体 | 申請中、審査中、修正依頼、許可、キャンセル申請中 | 不許可、キャンセル済み、全員の確認済み早期退去日の翌日以降 |
| 下書き | 確保しない | 提出時に空きを再検査 |

### 14.4 競合

- 個人同士は、各日の合計が15人未満であれば重複できる。
- 地域活動の団体は、他の団体、地域活動の個人、キャンプ、利用停止期間と重複できない。
- 同じ利用者は、重なる期間に複数の有効な宿泊申請を提出できない。
- 重複判定の対象は、申請中、申請済み、審査中、修正依頼、許可、キャンセル申請中とする。申請種別に存在しない状態は読み替える。
- 提出時の空き確認と枠確保を一つの処理として行う。
- 同時に両立しない申請が送信された場合は、先に登録処理を完了した申請を有効とし、後の利用者へ日程の再選択を案内する。

## 15. 審査・修正・履歴

- 申請詳細を閲覧しただけでは「審査中」に変更しない。
- 個人申請と参加者個別申請は、職員が「審査を開始する」を実行した時点で「審査中」にする。
- 団体全体は、予定する全参加者の提出完了時に自動で「審査中」にする。
- 修正依頼と不許可では理由の入力を必須とする。
- 許可時の職員コメントは任意とする。
- 利用者は、自分の申請が「下書き」または「修正依頼」の場合だけ編集できる。
- 職員だけが閲覧・編集できる内部メモ欄を設ける。
- 操作履歴に、操作者、変更対象、変更前後の状態、日時を記録する。
- 職員は全履歴を閲覧できる。
- 利用者は、自分の申請の状態変更履歴を閲覧できる。
- 複数職員が同じ申請を更新する場合は、最終更新日時を確認する。
- 別の職員による更新後の古い画面から保存しようとした場合は保存を止め、最新情報の再読込みを案内する。
- 職員同士の排他的な編集ロックは設けない。

## 16. 料金と納付

### 16.1 料金計算

料金は、1人につき1日300円とする。開始日と終了日の両方を使用日数へ含めるため、1泊2日は600円となる。

月をまたぐ申請は暦月ごとに分割し、1件の申請・1人・1か月につき、次の式で計算する。

**月内料金 ＝ 月内の使用日数 × 300円と9,000円の小さい方**

| 期間 | 計算 | 合計 |
|---|---|---:|
| 8月15日〜9月15日 | 8月17日分＝5,100円、9月15日分＝4,500円 | 9,600円 |
| 8月1日〜8月31日 | 31日分＝9,300円を月上限へ補正 | 9,000円 |
| 1泊2日 | 2日分×300円 | 600円 |

- 月9,000円の上限は利用者の月間合計ではなく、申請ごとに適用する。
- 同じ月に複数の申請があっても合算しない。
- 例として、8月1日〜20日の申請は6,000円、8月21日〜31日の別申請は3,300円となり、合計は9,300円となる。
- スパルタキャンプ利用は、期間中の一時不在にかかわらず固定期間全体で計算する。
- 団体利用は各参加者の個別申請ごとに料金を計算する。
- 団体代表者には団体全体の見込合計額と納付済み人数を表示し、参加者ごとの個人情報を表示しない。

### 16.2 納付

- オンライン決済は行わない。
- 町が発行する納付書を使い、指定金融機関の窓口で納付する現行方法を維持する。
- 職員が申請ごとに納付期限と「未納」「納付済み」を登録する。
- 利用者は料金、納付期限、納付状態を確認できる。
- 納付期限を過ぎた未納は「期限超過」と表示する。
- 納付状態によって審査状態または滞在状態を自動変更しない。

## 17. 入退去と緊急連絡

- 申請を許可した時点で滞在状態を「入居前」にする。
- 職員が対面で入居を確認し、「滞在中」へ変更する。
- 職員が対面で施設・設備を確認し、「退去済み」へ変更する。
- 退去時に問題がある場合の説明は対面・口頭で行うため、問題有無や説明内容の入力機能は設けない。
- 「滞在中」の利用者画面に、町の緊急連絡先名、電話番号、対応時間を表示する。
- 許可後の団体代表者にも同じ連絡先を表示する。
- 緊急連絡先は職員が設定・変更できる。

### 17.1 早期退去

- 予定より早く退去する場合は、利用者または団体代表者が町へ連絡する。
- 対面確認後、職員が「退去済み」へ変更する。
- 滞在開始後はキャンセル申請ボタンを表示しない。
- 元の許可期間と料金は変更せず、履歴として保持する。
- 地域活動の個人利用では、確認した退去日の翌日以降の定員を解放する。
- 地域活動の団体利用では、全参加者の退去確認後にだけ翌日以降の日程を解放する。
- スパルタキャンプ期間は、利用者が早期退去しても地域活動利用へ開放しない。
- 減額または返金は自動処理せず、町への確認事項とする。

## 18. 継続滞在・期間延長

- 元の申請を変更せず、追加期間だけを別申請として作成する。
- 延長申請を元の申請へ紐づける。
- 追加期間は、原則として元の退去日の翌日から開始する。
- 元のプロフィールと申請共通情報を初期表示し、変更内容または延長理由を入力させる。
- 次のスパルタキャンプへ参加する場合は、職員が設定した次のキャンプ期間を使用する。
- 地域活動を理由に継続する場合は、地域活動利用のカレンダーから期間を選ぶ。
- 延長先の利用区分に従い、空き状況、利用資格、審査、部屋割りを改めて確認する。
- 延長が許可されるまで、元の許可期間を変更しない。
- 延長申請は別申請として料金を計算し、同じ月でも元の申請と延長申請のそれぞれに月9,000円上限を適用する。

## 19. 職員管理機能

### 19.1 申請一覧

- 氏名、団体名、利用期間で検索できる。
- 利用区分、審査状態、納付状態、滞在状態で絞り込める。
- 受付番号、利用期間、人数、料金、納付、滞在など、業務に必要な概要を表示する。

### 19.2 申請詳細

- 様式第1号に対応する申請内容を確認できる。
- 審査開始、修正依頼、許可、不許可、キャンセル確定を操作できる。
- 修正理由、不許可理由、任意の許可コメントを登録できる。
- 部屋割り、料金、納付期限・状態、滞在状態を更新できる。
- 団体全体と参加者個別申請を関連付けて確認できる。
- 職員内部メモと操作履歴を確認できる。

### 19.3 日程・設定

- スパルタキャンプ期間、対象メール、申請期限を管理できる。
- 利用停止期間と内部向け理由を管理できる。
- 町の緊急連絡先名、電話番号、対応時間を管理できる。
- 既存申請と競合する日程変更を防止し、影響する申請を表示する。

## 21. 通知

### 21.1 必須

- 申請状態、修正理由、許可・不許可、提出期限、修正期限をアプリ内で確認できる。
- 団体招待は共通リンクまたはコードを代表者が共有する。
- 自動メールを実装していない場合でも、必要な情報をアプリ内で確認できる。

### 21.2 時間があれば追加

1. パスワード再設定メール
2. 修正依頼・許可・不許可のメール通知

メール通知を追加する場合の宛先は次のとおりとする。

| 通知 | 宛先 |
|---|---|
| 個人申請の修正依頼・許可・不許可 | 該当する本人 |
| 団体全体の修正依頼・不許可 | 団体代表者 |
| 団体参加者の個別申請 | 該当する参加者 |
| 団体全体の許可 | 団体代表者と全参加者 |

団体招待メールと期限前通知メールは追加対象に含めない。

| データ | 主な内容 |

| 職員権限 | 職員としての権限 |

| キャンプ対象者 | キャンプ、対象メールアドレス |
| 利用停止期間 | 開始日、終了日、内部理由 |
| 個人申請 | 利用区分、申請者・使用者情報の写し、期間、目的、状態、元申請 |
| 団体申請 | 代表者、団体共通情報、予定人数、状態、期限 |
| 団体参加者 | 団体、参加者、個別申請、参加状態 |
| 招待 | 団体、推測困難なトークン、有効期限、有効・無効 |

アカウント削除後も申請記録を保持できるよう、申請時点の氏名などを申請データの写しとして保持し、認証アカウントとの関連を解除できる設計にする。

### 22.1 整合性制約

- 空き確認と枠確保は同じトランザクションで処理する。
- 部屋別定員と施設全体15人をデータベース側でも検査する。
- 同一利用者の重複申請を禁止する。
- 団体の参加人数と部屋割り人数を一致させる。
- 団体全体をキャンセルする場合は、未終了の参加者申請も一括処理する。
- 更新日時を使い、古い画面からの上書きを防ぐ。
- 保護者同意書は公開URLで保存しない。
- 認証アカウント削除後の過去記録を、新しいアカウントへ自動で関連付けない。

## 23. 非機能要件

### 23.1 対応端末・ブラウザ

- 利用端末を限定せず、すべての画面をレスポンシブ対応とする。
- 職員画面はパソコンでの利用を主に想定するが、スマートフォンでも操作できるようにする。
- 最新版のChrome、Safari、Edgeを対象とする。
- iPhoneのSafari、AndroidのChrome、職員用パソコンのChrome・Edgeを主な確認環境とする。
- Internet Explorerは対象外とする。

### 23.2 性能

- 通常の通信環境で、主要画面をおおむね3秒以内に表示することを目標とする。
- 一覧やカレンダーは必要な期間・件数だけ取得する。
- 処理中は読み込み状態を表示する。
- 試作版では厳密な性能保証と本番規模の負荷試験を行わない。

### 23.3 アクセシビリティ

- 読みやすい文字サイズと十分な色のコントラストを確保する。
- 入力欄にラベルを付ける。
- 主要操作をキーボードで行えるようにする。
- エラーや状態を色だけに依存せず、文字でも説明する。
- 試作版では厳密なJIS適合試験を行わない。

### 23.4 セキュリティ・プライバシー

- VercelのHTTPS環境で公開する。
- SupabaseのRow Level Securityで閲覧・更新権限を制御する。
- 同意書は非公開Storageへ保存する。
- Supabaseの接続情報などは環境変数で管理し、GitHubへ登録しない。
- 認証アカウントの削除など管理権限が必要な処理はサーバー側で実行し、Supabaseの管理用秘密鍵をブラウザへ渡さない。
- 職員だけが見られる情報を一般利用者向けAPIから取得できないようにする。
- デモには実在する個人情報を使用しない。

### 23.5 信頼性

- 二重送信を画面側とサーバー側の両方で防止する。
- 定員または排他的利用の競合時は、後から完了した処理を失敗させ、理由を表示する。
- 更新競合時は上書きせず、最新状態の再読込みを求める。
- 自動期限処理では、団体全体、参加者申請、カレンダー枠を一貫して更新する。

## 26. 受入条件

### 26.1 業務シナリオ

次の操作を最初から最後まで完了できること。

1. 職員がキャンプと対象メールを登録し、対象者が申請し、職員が審査・部屋割り・許可・納付・入退去を管理できる。
2. 地域活動の個人利用者が日程を選び、申請、修正、許可、キャンセルまたは入退去まで操作できる。
3. 団体代表者が団体を作成して日程を確保し、参加者を招待し、全員が個別申請を提出し、職員が団体を審査・許可・入退去処理できる。
4. 修正依頼、再提出、不許可、キャンセル、提出期限切れ、修正期限切れを処理できる。
5. 継続滞在を追加期間の別申請として作成し、再審査できる。

### 26.2 計算・制御

- 1泊2日を600円と計算できる。
- 8月15日〜9月15日を9,600円と計算できる。
- 8月1日〜8月31日を9,000円と計算できる。
- 同月の別申請へ月上限を別々に適用できる。
- 各部屋の定員と施設全体15人を超える許可・割当てを防止できる。
- 下書きが日程を確保しない。
- キャンセル申請中は、職員が確認するまで枠を維持する。
- 個人利用は15人まで重複でき、団体利用は期間を排他的に確保できる。
- 同時送信でも定員超過または排他的な重複が生じない。
- 早期退去後のカレンダー枠だけを解放し、元の許可期間と料金を保持できる。

### 26.3 権限・個人情報

- 未ログイン画面へ申請者名、団体名、申請状態、利用不可の内部理由が表示されない。
- 団体代表者が参加者の住所、電話番号、緊急連絡先、同意書を閲覧できない。
- 一般利用者が職員権限を取得できない。
- 同意書を本人と職員以外が閲覧できない。
- 利用終了後の条件を満たした場合だけアカウントが初期化され、管理記録が職員向けに保持される。

### 26.4 画面・操作

- スマートフォンとパソコンの双方で主要操作を完了できる。
- 入力エラー時に入力内容が保持され、該当項目に理由が表示される。
- 送信成功時に受付番号、提出日時、状態が表示される。
- 状態や利用可否が色だけに依存せず判別できる。

## 27. 画面設計時に決める事項

次の事項は試作版の要件および業務ルールに影響しないため、画面設計時に決める。

- ログイン後に最初に表示する具体的な画面
- トップ画面の2つの利用区分への入口の配置、色、大きさ、最終文言
- 各画面の詳細なレイアウト
- カレンダーの具体的な配色と斜線表現

確定している上位要件は、ログイン後に自分の申請状況と必要な操作を確認できること、およびトップ画面から2つの利用区分へ進めることである。
