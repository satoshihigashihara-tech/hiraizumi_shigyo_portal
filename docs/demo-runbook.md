# 5役割の発表デモ手順

発表では全機能を順番に操作せず、「申請する人」「団体をまとめる人」「町職員」の流れが伝わる最短経路を使う。実在情報、秘密値、管理画面の内部IDは映さない。

## 架空アカウント

| 役割 | 用途 | 事前状態 |
|---|---|---|
| 1. キャンプ申請者 | 対象者限定申請 | 架空キャンプの対象メールへ登録済み |
| 2. 地域活動・個人利用者 | 空き日程から個人申請 | active、プロフィール入力済み |
| 3. 団体代表者 | 団体作成・招待 | active、代表者は宿泊しない設定 |
| 4. 団体参加者 | 招待参加・個人情報提出 | active、代表者とは別ブラウザを使用 |
| 5. 町職員 | 審査・部屋・納付・入退去 | `staff_roles`登録済み |

メールアドレスやパスワードそのものはこの文書へ書かず、発表者だけが使えるパスワード管理手段に保存する。

## 発表前に準備するもの

- 空き日程を使う架空キャンプ1件
- 個人利用の提出済み申請1件
- 参加者提出済みの架空団体1件
- 許可済み・入居前の申請1件
- 納付状態と料金が見える申請1件
- 保護者同意書は架空PDFのみ
- 利用者用と職員用でブラウザプロファイルを分ける
- 予備として主要画面のスクリーンショットを用意する

## 7〜10分のデモ進行

1. 未ログインでトップと公開カレンダーを表示し、個人情報が出ないことを説明する。
2. 個人利用者でログインし、自分の申請一覧、状態、期限、料金を表示する。
3. 空き日程から地域活動の下書き→確認→提出を短く見せ、受付番号と提出日時を確認する。
4. 団体代表者で参加人数・日程を表示し、招待コードを発行する。平文は一度だけ表示されることを説明する。
5. 別ブラウザの参加者で招待へ参加し、自分の情報だけを提出する。
6. 代表者へ戻り、参加状況だけが見え、住所や緊急連絡先が見えないことを示す。
7. 職員で審査画面を開き、目的確認、部屋割り、許可、料金・納付を表示する。
8. 許可済み申請の入居→退去を処理し、カレンダー解放と管理記録保持を説明する。
9. 「期限・定員・権限・同時操作はDBでも防御し、自動テスト済み」とまとめる。

## デモ中に変更しないもの

- SupabaseのSecret key、Vault、Auth管理画面
- 実在利用者のメール・氏名・住所・電話
- 本番用マイグレーション、職員権限、アカウント初期化のCron設定

## 失敗時の切替

- ログインに失敗：別の架空アカウントへ切り替え、原因調査は発表後に行う。
- 外部通信が遅い：事前スクリーンショットで画面遷移を説明する。
- 申請状態が予定と違う：DBを直接変更せず、別の準備済み申請を使う。
- 自動削除関連の異常：[障害時の緊急対応](incident-runbook.md)の停止手順へ移る。

## 発表後

- デモで作成した架空データのIDを記録する。
- 画面操作で安全に取消・終了できるものだけ処理する。
- SQLで直接削除しない。削除が必要なら対象と関連記録を確認して別作業にする。
