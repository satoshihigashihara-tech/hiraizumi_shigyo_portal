SQL 009は初回提出と修正再提出の期限を分け、ロック取得後の現在時刻で期限を判定します。修正期限未設定・期限切れ・キャンプ日程変更時の再提出を拒否します。SQL 011は下書き作成入口の時刻を `now()` から `clock_timestamp()` へ変更します。両方とも既存Actionの名前・入力項目は維持しています。

検証結果：2026年9月10日、SQL 001〜011適用後にユーザーが `supabase/tests/camp_room_allocations_and_approval.sql` 全体をSQL Editorで再実行しました。15:42の提供画像で `passed_checks = 218` と単一接続の表示を確認しました。初回に失敗した下書き作成入口の期限拒否は、SQL 011で修正後、追加ケースとともに通過しました。確認範囲は第4.4節に記載します。

検証SQLは架空データと一時ヘルパーを使い、`authenticated`／`anon` へ権限を切り替えてRPC・RLSを検査します。履歴書込みの失敗を起こす検証用トリガーも含め、末尾の `ROLLBACK` で検証用変更を取り消します。Authの実ログイン、JWT署名検証、Storageの実ファイル検証、複数接続での同時更新はこの218項目には含みません。当時はローカルのPostgreSQL実行環境・直接DB接続は未設定でした。今回のSQL 012検証用に一時的なローカルDBを用意しました（第4.6節）。

コードの確認：`npm run lint`・`npm run build`・`git diff --check` は成功しています。SQL 009・011は元の関数との差分を静的に確認しました。職員Actionの一時的な検証では34項目が成功しました（認証ガード、入力拒否、更新日時のマイクロ秒保持、RPC引数、エラー変換、表示更新等）。この34項目はSupabaseと認証ガードを代替しており、DBの検証結果とは区別します。

### 4.4 キャンプの部屋割り・審査の接続（SQL 010）

対象は職員の `/staff/camps/[campId]/applications/[applicationId]` です。キャンプ個人だけを扱い、部屋は1申請1部屋・1人・キャンプの固定期間全体です。人数と日程をフォームから保存しません。地域活動・団体・利用停止期間との枠管理全体はT09以降の残作業です。

`updatedAt` には、画面を表示したときに取得した `applications.updated_at` の文字列をそのまま渡します。`new Date(...).toISOString()` 等でマイクロ秒を丸めたり、送信直前に最新の値へ置き換えたりしないでください。部屋割り成功後は親申請の更新日時も変わるため、最新の詳細を読み直してから許可します。SQL 010は旧3引数の `review_camp_application` を削除します。ActionとSQLをそろえずに接続すると審査を実行できません。

| RPC | 引数 | 返却列 |
|---|---|---|
| `assign_camp_application_room` | `target_application_id`、`target_room_id`、`expected_updated_at`、任意の `change_reason` | `result_camp_id`、`result_status`、`result_updated_at` |
| `review_camp_application` | `target_application_id`、`review_action`、`expected_updated_at`、任意の `public_reason` | 上記3列と `result_revision_due_at` |

審査操作は `start_review`・`request_revision`・`reject`・`approve` の4種類です。修正・不許可の理由、許可コメント、部屋変更理由は最大2,000文字です。初回の部屋割りは審査中に行い、理由は任意です。既存割当の部屋変更は審査中・許可後とも理由必須です。許可後は入居前・滞在中だけ変更でき、退去済みの割当は変更しません。修正依頼中は割当を維持し、不許可では `released_from = start_date` として全日を解放し、割当行と履歴を残します。

許可時は部屋・1人・全期間・未解放・日別定員を再確認し、申請状態、`stays.before_move_in`、状態履歴、監査履歴を同じトランザクションで保存します。部屋変更は料金・納付・滞在状態を変更しません。同じ部屋の保存は、更新日時が最新なら何も更新せず、履歴も追加しません。古い更新日時での再送は `stale-update` となり、許可や履歴を二重作成しません。

読取は既存RLSを使います。部屋一覧は `rooms` の `id,name,capacity`、本人の結果は `room_allocations` の部屋・人数・日程を取得します。状態履歴は本人向けに `from_status,to_status,public_reason,occurred_at` だけを返し、職員IDを含めません。職員専用の `audit_logs` は `entity_type='application'` と `entity_id=applicationId` で絞り、`action,before_data,after_data,reason,actor_user_id,occurred_at` を取得します。部屋の内部変更理由は利用者向け状態履歴へ転記しません。監査の追加対象は今回の職員操作だけで、他機能の監査はT15の残作業です。

主なエラーの日本語案内：

| エラー | 表示・次の操作 |
|---|---|
| `invalid-version`・`stale-update` | 最新の情報を再読み込みし、内容を確認してから操作してください |
| `room-required` | 許可する前に部屋を割り当ててください |
| `room-capacity-full` | 選択した期間の部屋定員を超えます。割当状況を確認してください |
| `facility-capacity-full` | 施設全体の定員15人を超えます。申請状況を確認してください |
| `reason-required`・`reason-too-long` | 理由を入力／理由またはコメントを2,000文字以内に修正してください |
| `invalid-status`・`stay-completed` | 現在の申請・滞在状態では操作できません |
| `invalid-room` | 部屋を選び直してください |
| `camp-unavailable`・`camp-dates-changed` | キャンプ設定が変更されています。最新の期間と申請内容を確認してください |
| `invalid-allocation`・`invalid-stay` | 割当・滞在情報が整合していません。管理担当者へ確認してください |
| `forbidden`・`not-found` | 職員権限または対象申請を確認してください |
| `invalid-action`・`update-failed` | 更新できませんでした。再読み込みして確認してください。内部情報は表示しません |

検証ファイル：[camp_room_allocations_and_approval.sql](../supabase/tests/camp_room_allocations_and_approval.sql)。更新後のファイルはSQL 001〜011を必要とします。検証用SupabaseプロジェクトでSQL 009→010→011を適用した後、SQL Editorの `postgres` ロールでファイル全体を1接続で実行します。成功時は検査結果一覧と件数を確認します。途中でエラーが出た場合はその検査を失敗と扱い、同じ接続で `ROLLBACK` してから原因を調べます。最後の `ROLLBACK` を `COMMIT` に変更したり、一部だけを選択して実行したりしないでください。検証中は施設ロックを保持するため、他の利用者が操作していない検証用環境を使います。

SQL 011に対応する検証として、期限前の下書き作成・再利用、未ログイン・停止中・対象外の拒否、採番・料金・割当・滞在の非作成、履歴の重複防止、期限後の既存下書き再利用・新規作成の拒否を追加しました。元の失敗ケースは維持しています。修正再提出の成功ケースの初回期限は、旧処理の `now()` でも確実に過去となるようトランザクション開始前へ設定し、旧実装へ戻った場合も検査で検出できるようにしました。更新後の検証SQLは218項目成功しました（ユーザー提供画像で確認）。

テストはDBの役割・セッション情報を設定してRPC・RLSを実行しますが、Authへの実ログインやJWT署名検証の代わりにはなりません。同意書は架空メタデータで検査するため、Storageの実ファイル検証はT06で別途必要です。SQL 009の期限を現在時刻に設定した拒否ケースは含みますが、`clock_timestamp()` と修正期限のマイクロ秒単位の完全一致や、ロック待ち中の期限超過を実証するものではありません。

DBでの検証項目（単一接続218項目と、第4.5節の複数接続7ケースは成功）：

- SQL 009の期限境界、再提出の受付番号維持、同意書・料金・履歴。初回期限後の修正再提出をSQL 008相当の審査フローから通す。
- 各部屋の定員ちょうどの割当と、次の1人の拒否。開始日・終了日を含む日別検査、別期間の同じ部屋の利用。
- 別キャンプを含む施設15人の検査、部屋未割当の申請・修正依頼中・キャンセル申請中の人数の算入。
- 未ログイン、一般利用者、停止中職員、他人の申請、部屋・申請・滞在・監査履歴への直接書込みの拒否。利用者による監査履歴読取の拒否。
- 下書きや申請済みからの直接許可、部屋未割当・日程不一致・解放済みの許可の拒否。正常な許可時の入居前・状態履歴・監査履歴の一致。

- 複数DB接続で、残り1枠の部屋への同時割当は1件だけ成功すること。同じ申請への変更・許可の競合や二重送信は古い更新日時を拒否すること。マイクロ秒だけ異なる値も区別すること。

ファイル全体の実行は準備だけです。`postgres` 専用の `t12_concurrency_test` スキーマと、架空の利用者25人（職員2人を含む）・キャンプ7件・申請23件を作ってコミットします。専用テーブルにはRLSを有効にし、スキーマ・テーブル・関数・プロシージャの権限を一般利用者・職員・service_roleへ開放しません。対象RPCだけを `authenticated` と架空の認証情報へ切り替えて呼びます。Auth・Storage API、パスワード、追加拡張は使いません。

準備後は別々のSQL Editorタブに次のSQLを用意します。1つのクエリには該当する `CALL` だけを置き、`BEGIN` で囲みません。Aを実行し、Aが実行中のまま30秒以内にBを実行します。各処理はケース間でコミットし、相手の待機・完了を確認しながら7ケースを進めます。[PostgreSQLのプロシージャとトランザクション制御](https://www.postgresql.org/docs/current/plpgsql-transactions.html)

```sql
-- 接続Aのクエリ
call t12_concurrency_test.worker_a();
```

```sql
-- 接続Bのクエリ
call t12_concurrency_test.worker_b();
```

| ケース | 接続A・Bの操作 | 確認する結果 |
|---|---|---|
| 1 | 別の申請を同じ1人部屋へ割当 | Aだけ成功し、Bは `room-capacity-full` |
| 2 | Aが部屋変更、Bが同じ申請を許可 | Aの変更を残し、Bは `stale-update` |
| 3 | 同じ申請を同時に許可 | 許可・入居前・履歴が1件で、Bは `stale-update` |
| 4 | 同じキャンプの有効申請14件に対し2件を同時提出 | 合計15人で止まり、Bには受付番号・料金を作らない |
| 5 | ケース2をBの `REPEATABLE READ` で実行 | 古いDBスナップショットはSQLSTATE `40001` |
| 6 | 修正期限前にBが再提出、Aのロックで期限後まで待機 | Bは修正期限切れ。元の申請・割当・受付番号・料金・履歴を維持 |
| 7 | Bの職員操作が待機中にAがその職員を停止 | 再検査で `42501 / staff-required`、更新・監査追加なし |

Aは `pg_blocking_pids()` で自分がBを待機させていることを確認し、双方のDB接続IDと時刻を記録します。検証時はその一致と、失敗したBによる部分更新がないことを確認します。処理内の待機には50秒の予算があり、競合が確認できない場合は成功と扱いません。SQL Editorがクエリを直列化したり `CALL` をトランザクションで囲んだりする環境では、この方法は使えません。その場合は環境側の失敗と区別し、2つの直接DB接続で実施する必要があります。[待機接続の取得](https://www.postgresql.org/docs/current/functions-info.html)、[監視情報の更新](https://www.postgresql.org/docs/current/monitoring-stats.html)

両方が終了したら `select * from t12_concurrency_test.verify();` を実行します。7行すべての `passed = true`、A・Bの異なる接続ID、期待する拒否コードを確認して結果を記録します。

結果確認後、準備の結果に表示される後片付けSQLを実行します。失敗時にも、両方の処理が停止したことを確認したうえで実行できます。

```sql
begin;
select t12_concurrency_test.cleanup();
drop schema t12_concurrency_test cascade;
commit;
```

後片付けは記録したUUID・架空メール・実行識別子を照合し、予期しない参照・添付・ログイン履歴があれば停止します。該当する架空の申請・関連行・キャンプ・利用者と専用スキーマだけを削除します。受付番号カウンターは再利用を避けるため巻き戻さず、テストで消費した番号は欠番になります。既存の業務関数・RLS・部屋マスターは変更しません。

途中で失敗した場合、エラーが出た接続で `ROLLBACK` し、両方が停止するまで待ってから後片付けします。片側だけを再実行せず、後片付け後にファイル全体から準備し直してください。専用スキーマが残っている場合、新しい準備は上書きせず停止します。
