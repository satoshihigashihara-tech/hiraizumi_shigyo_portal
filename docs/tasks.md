## 1. 最初に読むこと

現在は、認証・キャンプ申請・保護者同意書の**サーバー処理とデータベース定義の一部がある段階**です。画面は `app/page.js` のNext.js初期テンプレートだけで、利用者・職員の業務画面はありません。申請から入退去まで使える完成状態ではありません。

この一覧は、[要件定義](requirements.md)、[画面・URL設計](routes.md)、[データベース設計](database.md)と、現在のソースを照合したものです。SQL `001`〜`007` のSupabaseへの適用、非公開Storageバケットの設定、`npm run lint` と `npm run build` の成功は2026年9月10日に確認しました。デモ用の職員・キャンプ利用者アカウントと対象キャンプも登録済みです。ただし、利用者・職員画面が未作成のため、ブラウザからの一連の操作とVercel公開は未確認です。

| 表記 | 意味 |
|---|---|
| 実装済み | 記載した範囲のコード・SQLが存在する。実環境での動作確認済みという意味ではない |
| 作業中 | 一部の処理・テーブルはあるが、要件を満たすには残作業がある。誰かが現在着手していることを断定しない |

| フロント担当 | 画面、入力フォーム、表示、画面遷移を作る人 |
| バックエンド担当 | 保存処理、DB、認証・権限、料金・定員などの業務ルールを作る人 |

担当は2人開発を想定した**仮の役割分担**です。実名・着手日・期限は資料にないため未確定です。以下の「完了条件」は今後の確認基準であり、達成済みの報告ではありません。

用語：DBはデータの保存先、SQLマイグレーションはDB構造を順番に作るファイル、Server Actionは画面から呼ぶサーバーの更新処理、RPCはDB内の処理を呼ぶ仕組み、RLSはDB側で「誰がどのデータを見られるか」を制限する仕組みです。

## 4. フロント担当が接続を始めるためのメモ

### 4.1 既存Actionの入力と動き

以下は現在のコードの契約です。設計との差分は第5章で修正対象として管理します。Action名が存在しても、遷移先ページは未作成です。

| ファイル／Action | 渡す値（フォームの `name`） | 現在の成功時の動き |
|---|---|---|
| `app/actions/auth.js`：`login` / `signUp` | `email`、`password`、任意の `returnTo` | 利用者は `/user`、職員ログインは `/staff`、条件を満たす招待経由は招待先へ戻る |
| 同上：`logout` | 引数なし | `/login` へ移動する（設計では `/`） |
| `app/actions/staff-camps.js`：`createStaffCamp` | `campName`、`startDate`、`endDate`、`applicationDeadline` | `/staff/camps/[campId]` へ移動。期限入力は `YYYY-MM-DDTHH:mm` を日本時間として変換 |
| 同上：`addCampEligibleUsers` | `campId`、`eligibleEmails` | 対象者画面へ登録件数などをクエリで返す。メールは改行・空白・カンマ・セミコロン区切りに対応 |
| `app/actions/camp-applications.js`：`createCampApplicationDraft` | `campId` | `/user/applications/[applicationId]/edit` へ移動 |

### 4.2 エラーと表示データ

- 現在の更新Actionは主に `?error=...` を付けて移動します。認証には `required`・`invalid`・`short`、キャンプ申請には `deadline-passed`・`not-eligible`・`capacity-full`・`required-fields`・`invalid-phone`・`guardian-consent`、添付には `file-required`・`invalid-size`・`invalid-type`・`invalid-content`・`upload-failed` などがあります。完全な一覧は各Actionの分岐を参照し、コード文字列をそのまま表示せず日本語の案内にします。
- 現方式だけでは、保存に失敗した入力値の保持や項目別エラーを満たしません。T05・T23で、フロントとバックエンドが入力値・項目別エラーの受け渡し方式を決めます。
- 読取画面はまだありません。サーバー用SupabaseクライアントとRLSを使い、本人・職員の権限内で必要な列だけを取得します。更新は用意されたAction／RPCを使います。
- 申請状態、納付状態、滞在状態は別々に表示します。「申請済み」は「許可」ではありません。完了URLの受付番号だけを根拠に提出成功を表示しないでください。
- 接続に必要な変数名は `NEXT_PUBLIC_SUPABASE_URL`、`NEXT_PUBLIC_SUPABASE_ANON_KEY`。添付保存の管理用 `SUPABASE_SECRET_KEY` はサーバー専用です。値はこの文書に記載しません。

## 6. おすすめの進め方と完了の扱い

1. **環境と既存処理を確認する**：T01、第5章のSQL実行・同意書の課題を先に確認する。フロントは並行してT07と認証画面の枠組みを作れる。
2. **キャンプで最初の一連の操作をつなぐ**：T02〜T08で職員登録→利用者提出までをつなぎ、T11〜T15で審査・部屋割り・納付・入退去まで進める。
3. **日程管理と地域活動を追加する**：T09〜T10、T16〜T17を進める。定員・日程整合性の確認が終わるまで複数利用者の受付を公開しない（DB設計12章）。
4. **団体と自動処理を追加する**：T18〜T22を進め、専有枠・個人情報の制限・期限処理を組み合わせて確認する。
5. **全体を受け入れ確認する**：T23〜T24で3つの利用区分を通し、権限・同時更新・日付境界も確認する。T25は本運用前に完了する。

各タスクを更新するときは、状態・担当・残作業・検証結果・フロントへの引き渡し状況を一緒に更新します。機能全体を「実装済み」に変更するのは、その行の完了条件を画面と保存処理の両方で確認してからです。未確認なら「コードあり・動作未確認」と残してください。
